# Direct Sale: ติดตามลูกค้าที่มี Potential และวัดยอดจากการติดตาม — Design

วันที่ 2026-11-23 · สถานะ: รอผู้ใช้ตรวจ · ต่อจาก `2026-11-17-direct-sale-design.md` (ข้อ 6 กติกานับยอด) และ `2026-11-20-jst-outreach-worker-design.md`

## 1. เป้าหมาย

ให้หน้า **Direct Sale** (`/leads`) เป็นที่ติดตามลูกค้าที่มี Potential อย่างใกล้ชิด ขุดซ้ำได้จากหน้าเดียว (โทร / แชต JST / Meta / ส่งข้อความ) และ**ใช้วัดยอดขายที่เกิดจากการติดตาม** รวมถึงกรณีเซลล์แชตเองใน JST

## 2. Flow การทำงาน

```
ฐานลูกค้าเก่า ─┬─ tag Admin_* ใน JST ─┐
               └─ เซลล์จองจากถังกลาง ─┴─▶ [1] ลูกค้าของฉัน (/mine) — เซลล์คัดกรอง
                                              │ ติ๊กคนที่มี Potential → "เข้า Direct Sale"
หัวหน้าส่งจากแคมเปญ ─────────────────────────┼──────────────┐
                                              ▼              ▼
                                   [2] Direct Sale (/leads) — ติดตาม/ขุดซ้ำ
                                       โทร · แชต JST · Meta Inbox · ส่ง template · บันทึกผล · Refresh
                                              ▼
                                   [3] วัดผล — ยอดจากการติดตาม ต่อเซลล์ → Dashboard + Project Commission
```

## 3. การตัดสินใจ (ผู้ใช้ยืนยัน 2026-11-23)

| # | เรื่อง | ตัดสินใจ |
|---|---|---|
| 1 | ลูกค้าจากแคมเปญ | เข้า Direct Sale ทันที (ไม่ผ่าน "ลูกค้าของฉัน") |
| 2 | ยอดที่นับ | เฉพาะลูกค้าที่อยู่ใน Direct Sale (มีลีดที่เซลล์เป็นเจ้าของ) |
| 3 | แชตที่เซลล์คุยเอง | ข้อความฝั่งร้านในห้องที่ผูกกับเบอร์ หลังลูกค้าเข้า Direct Sale = การติดตาม **แม้ลูกค้าทักมาก่อน** (ยกเลิกเกณฑ์ "เซลล์ทักก่อน" ข้อ 6.1.2 ของ spec เดิม) |
| 4 | ช่วงนับยอด | 30 วันหลังการติดตาม (`window_days` เดิม) |
| 5 | อัปเดตสถานะลีด | **ระบบย้ายสถานะให้เองทั้งหมดตามกติกา (ไม่ใช้ AI, ไม่ต้องกดยืนยัน)** ทั้งจากออเดอร์และจากแชต — ตารางกติกาข้อ 4 ส่วนที่ 2 · เซลล์แก้เองได้เสมอ และทุกการย้ายอัตโนมัติมีบันทึกเหตุผลให้ย้อนดู (แก้เมื่อ 2026-11-23 จากเดิม "ออเดอร์อัตโนมัติ แชตเป็นข้อเสนอ") |
| 6 | ข้อมูลแชต | **ทาง A**: worker ดึงข้อความจาก JST เก็บในตารางของเราเอง (ตามคำขอ Refresh + รอบอัตโนมัติของลูกค้าใน Direct Sale) — ข้อความใน `iim_messages` (cache ของระบบอื่น) ขาดห้องส่วนใหญ่ (สุ่ม 32 ห้อง ไม่อยู่ใน cache 31 ห้อง) |
| 7 | AI อ่านแชต (สรุป/แนะนำสถานะ) | ไม่ใช้ตอนนี้ — เริ่มด้วยกติกา (ไม่มีค่าใช้จ่าย) แล้วค่อยพิจารณาส่วนที่ 4 เมื่อมีข้อมูลจริงว่ากติกาผิดบ่อยแค่ไหน (ตัวเลือก: Claude API หรือโมเดล open-source บนเครื่องของเรา) |

## 4. แบ่งงานเป็น 4 ส่วน (แต่ละส่วนมีแผนของตัวเอง ทำตามลำดับ)

### ส่วนที่ 1 — เครื่องมือแชตในหน้า Direct Sale (รายละเอียดข้อ 5)
ไอคอนห้องแชตรายห้อง (JST / Meta Inbox) เหมือน `/mine`, ติ๊กลีดแล้วส่งข้อความผ่าน worker, ยืนยันว่าลีดแคมเปญขึ้นใน Direct Sale

### ส่วนที่ 2 — ดึงแชตด้วย worker + ปุ่ม Refresh
- ตารางใหม่ `dsales_chat_messages` (ms_id, msg_id, time, dir customer/admin, fmt, text ตัดสั้น, fetched_at) เก็บข้อความที่ worker ดึงจาก `/iim/getMsgs`
- คิวคำขอ `dsales_sync_requests` (lead/phone, requested_by, status) — worker ทำ: งานส่งข้อความ → คำขอ sync → ค้นห้องด้วยรหัสผู้ซื้อ · รอบอัตโนมัติ: ห้องของลีดใน Direct Sale ที่ sync เก่ากว่า N ชม.
- ปุ่ม **Refresh** ต่อแถว: อ่านออเดอร์ใหม่จาก DB ทันที + ส่งคำขอ sync แชต แล้วประเมินกติกาเมื่อ worker ตอบ · รอบอัตโนมัติ (ออเดอร์ทุกรอบ cron เดิม, แชตหลัง worker sync) ประเมินกติกาเดียวกันโดยไม่ต้องกด
- **กติกาย้ายสถานะอัตโนมัติ** (ไม่ใช้ AI) ประเมินเฉพาะเหตุการณ์ที่เกิด**หลัง**การเปลี่ยนสถานะครั้งล่าสุด (ถ้าเซลล์เพิ่งแก้สถานะเอง ระบบไม่ทับจนกว่าจะมีออเดอร์/ข้อความใหม่) · ถ้าเข้าหลายข้อในรอบเดียว ใช้ข้อที่อยู่บนสุด:

| ลำดับ | เห็นอะไรในข้อมูล | ย้ายเป็น |
|---|---|---|
| 1 | มีออเดอร์ใหม่หลังลูกค้าเข้า Direct Sale | **ปิดการขายแล้ว** + เติมเลขบิล/ยอด/วันที่ปิดให้เอง (ไม่ย้ายกลับ แม้ข้อความหลังจากนั้นจะเข้าข้ออื่น) |
| 2 | ข้อความลูกค้ามีคำในรายการ "ไม่สนใจ" (เช่น ไม่สนใจ, ไม่เอา, ยกเลิก) | **ไม่สนใจ** |
| 3 | ข้อความลูกค้ามีคำในรายการ "สนใจ" (เช่น สั่ง, โอนแล้ว, ราคาเท่าไหร่, มีของไหม) | **กำลังติดตาม** + ป้าย 🔥 "ลูกค้าสนใจ" ให้เซลล์รีบตาม |
| 4 | ลูกค้าตอบหลังข้อความล่าสุดของร้าน | **กำลังติดตาม** |
| 5 | ร้านทักแล้วลูกค้าเงียบเกิน X วัน (ค่าเริ่ม 3 วัน ตั้งได้) | **รอติดต่อ** (วันนัด = วันนี้) |

- รายการคำ "สนใจ / ไม่สนใจ" และค่า X เก็บใน `dsales_settings` หัวหน้าแก้ได้ในหน้าตั้งค่า
- ทุกการย้ายอัตโนมัติเขียน `dsales_interactions` (type `system`, เหตุผล เช่น "ลูกค้าพิมพ์ 'ไม่เอาค่ะ' 23/11 14:05") แสดงในประวัติของลีดให้เซลล์เห็นและแก้กลับได้
- ห้องที่ worker ไม่เคย sync และไม่มีใน `iim_messages` → ประเมินได้แค่ข้อ 1 (ออเดอร์)

### ส่วนที่ 3 — นับยอดจากการติดตาม
- การติดตามที่ผ่านเกณฑ์: โทร `connected` (บันทึกการโทร) · ข้อความ worker ที่ยืนยันแล้ว · ข้อความฝั่งร้านในห้องที่ผูกกับเบอร์ (จาก `dsales_chat_messages` + `iim_messages`) — ทุกแบบต้องเกิด**ขณะลูกค้าอยู่ใน Direct Sale** และลูกค้าไม่ซื้อมาแล้ว ≥ 30 วันก่อนการติดตาม (ข้อ 6.1.3 เดิม)
- ผู้ได้ผลงาน = เจ้าของลีด ณ เวลาการติดตาม (ชื่อผู้ส่งในแชตเป็นชื่อเพจ) → ต้องมีประวัติเจ้าของลีด `dsales_lead_owner_log` (trigger เมื่อ owner เปลี่ยน)
- บิล: ตามข้อ 6.3–6.4 ของ spec เดิม (bill_no ↔ order_tracking.phone, ทุกบิลใน 30 วัน, 1 บิลนับครั้งเดียว, ผูกการติดตามล่าสุดก่อนบิล) → `dsales_attributions` + job รันพร้อม cron เดิม + Dashboard ต่อเซลล์ + view ให้ Project Commission

### ส่วนที่ 4 — AI สรุปแชต (ทางเลือกภายหลัง)
ทำเมื่อกติกาของส่วนที่ 2 ผิดบ่อยจนเซลล์ต้องแก้เยอะ · ใช้ข้อความจาก `dsales_chat_messages` · ตัวเลือก Claude API (Haiku ~0.02 บาท/ลูกค้า, Opus ~0.77 บาท/ลูกค้า โดยประมาณ) หรือโมเดล open-source บนเครื่องของเรา · ต้องเช็กนโยบาย PDPA ก่อนส่งแชตออกนอกบริษัท

## 5. ส่วนที่ 1 — รายละเอียด

### 5.1 สิ่งที่มีอยู่แล้ว (ไม่ต้องทำใหม่)
- ลีดแคมเปญ (`dsales_leads.campaign_id`) ขึ้นใน Direct Sale แล้ว: `dsales_my_leads` คืนลีดที่ฉันเป็นเจ้าของ + ลีดแคมเปญที่ยังไม่มีเจ้าของให้จอง และหัวหน้ามอบหมายได้ (`dsales_assign_lead`) — การสร้างลีดจากเงื่อนไขแคมเปญ (criteria) เป็นงานค้างเดิมใน CLAUDE.md ไม่อยู่ในส่วนนี้
- ปุ่ม "เข้า Direct Sale" แบบติ๊กหลายคนใน `/mine` และไอคอนห้องที่คัดลอกชื่อห้อง/เปิด Meta Inbox (commit `98ae556`, `722223b`)

### 5.2 ข้อมูล
- RPC ใหม่ `dsales_rooms_for_phones(p_phones text[])` → `[{phone, rooms}]` โดย `rooms` = JSON เดียวกับ `dsales_customer_rooms` (ms_id, provider, page, brand, sendable, **name**, และ outer_user_id / meta_page_id / meta_business_id ของ FB/IG) · เรียก `dsales_uid()`, คืนเฉพาะเบอร์ของลีดที่ผู้เรียกเห็นได้ (เจ้าของ / หัวหน้า) · สูงสุด 100 เบอร์ต่อครั้ง
- รวม migration `dsales_customer_rooms_name` (ค้างอนุมัติ) เข้ามาในส่วนนี้
- หน้าเว็บโหลดห้องเฉพาะลีดที่แสดงในหน้า/ตัวกรองปัจจุบัน (ไม่โหลดทั้ง 1,000 ลีด) และโหลดใหม่เมื่อรายการเปลี่ยน

### 5.3 หน้าตา / การทำงาน
- **คอลัมน์ติดต่อในตาราง** (`LeadTable` → `ContactBar`): ปุ่มโทร + ไอคอนห้องรายห้องด้วย component เดียวกับ `/mine` (แยก `ChannelCell` เป็น `RoomIcons` ที่รับ phone/name/chat/brand/rooms) — ห้องที่ส่งได้สีปกติ ส่งไม่ได้จาง, FB/IG เกิน 24 ชม. ที่รู้ page id เปิด Meta Inbox พร้อมคัดลอกชื่อห้อง · ลีดที่ยังไม่มีห้องผูก ใช้ช่องทางแบบเดิม (`channelsOf`) เหมือนตอนนี้
- **popup รายละเอียดลูกค้า** (`ChannelRow`): แสดงห้องรายห้องแบบชิป (ไอคอน + เพจ + ชื่อห้อง) ทำงานเหมือนไอคอนในตาราง
- **ส่งข้อความ**: ช่องติ๊กหน้าแถว + ติ๊กหัวตาราง (ทั้งหน้า) + แถบลอยด้านล่าง "เลือก N คน · ส่งข้อความ" → `SendOutreachModal` เดิม (template, preview, คิว worker) · สูงสุด `outreach_max_batch` (50) · ติ๊กได้เฉพาะลีดที่ฉันเป็นเจ้าของ (ลีดแคมเปญที่ยังไม่จอง/ของคนอื่นไม่มีช่องติ๊ก)
- มือถือ (≤ 760px): ช่องติ๊กอยู่ในการ์ดลีด, แถบลอยปุ่มสูง ≥ 44px ไม่ล้นจอ 390px (ตาม `e2e/mobile-fit.spec.ts`)

### 5.4 Error / กรณีพิเศษ
- โหลดห้องไม่สำเร็จ: ใช้ช่องทางแบบเดิม ไม่แสดง error ทั้งหน้า (toast ครั้งเดียว)
- ส่งข้อความ: กติกาข้ามเดิมของ preview/enqueue (ไม่มีห้อง, เกิน 24 ชม., อยู่ในคิวแล้ว, ห้ามโทร)
- โหมด fixture: ลีดตัวอย่างไม่มีห้องผูก จึงใช้ช่องทางแบบเดิม (ContactBar) · ปุ่มเขียนข้อมูลแสดง toast โหมด fixture

### 5.5 ทดสอบ
- SQL test `12_rooms_for_phones.sql`: สิทธิ์ (เซลล์เห็นเฉพาะลีดของตัวเอง, หัวหน้าเห็นทั้งหมด), รูปแบบ JSON ตรงกับ `dsales_customer_rooms`, จำกัด 100 เบอร์, เวลา < 0.3 วินาที/100 เบอร์
- Unit (Vitest): map ห้องของลีด, เลือกได้เฉพาะลีดของฉัน, ข้อความแถบเลือก
- e2e: ภาพ `/leads` ที่ 1440/390 (อัปเดต baseline ตั้งใจ), ติ๊กแล้วแถบขึ้น, mobile-fit
